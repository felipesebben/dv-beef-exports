# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Market-intelligence tool for a Brazilian beef export trading company, built on [ComexStat](https://comexstat.mdic.gov.br) (Brazil's official foreign trade statistics, MDIC). Answers "what is Brazil selling, to where, and which markets look promising" from public trade data — company/importer-level discovery is an explicit non-goal of this data source (see `docs/ROADMAP.md` Phase 4).

Two-person coworking/learning project (see `docs/decisions/0001-initial-technical-foundations.md`), on GitHub Flow, iterating phase by phase per `docs/ROADMAP.md`.

## Architecture

`src/dv_beef_exports/` — `ingestion/` (pulling and loading ComexStat data), `analysis/` (Phase 2 opportunity scoring, see `docs/decisions/0005-opportunity-scoring-methodology.md`), `app/` (Streamlit prototype, Phase 3, surfaces `analysis/`).

**Ingestion pipeline** (`ingestion/`):
- `ncm_codes.py` — the 11 beef NCM codes this pipeline tracks, each tagged with a `category` (`frozen`, `offal`, `salted_dried`, `processed`). Fresh/chilled beef and live cattle/hides are deliberately excluded — different commodities/product lines (see ADR 0002).
- `comexstat_client.py` — `fetch_exports()` calls `POST /general` on `api-comexstat.mdic.gov.br` (no auth), requesting `?language=en` so country/NCM names come back human-readable directly. `fetch_countries()`, `fetch_economic_blocks()`, `fetch_country_blocs()`, `fetch_ncm_hierarchy()` call the `GET /tables/*` dimension endpoints — same host, same `Referer` header, no special `User-Agent` needed (that's only required for the interactive `/docs` HTML page itself). See `docs/comexstat-api-reference.md` for the confirmed endpoint/param reference (from the actual OpenAPI spec), including that the live `/tables/*` responses are thinner than the sample dimensional workbook (no ISO codes, no "Section" level). Raises `ComexStatError` (non-retryable: bad request, unexpected shape) or `ComexStatTransientError` (retryable via `tenacity`, 4 attempts, exponential backoff capped at 30s, shared by both the `POST /general` and `GET /tables/*` code paths via `_handle_response()`). **Both 403 and 429 are classified as transient** — the API sits behind a WAF that soft-blocks with undocumented, occasional 403s and 429s ("rate limited", found via live use, not something mocked tests caught).
- `duckdb_loader.py` — three schemas inside the tracked `data/processed/comexstat.duckdb` file, per `docs/decisions/0004-medallion-data-layering.md`:
  - `raw.exports` — append-only, minimal casting (every column but the provenance fields is `VARCHAR`, even ones that look numeric — the live response's actual field types are still unconfirmed). `ingest_raw()` never deletes or overwrites; every call stamps its rows with a fresh `pull_id`/`fetched_at`, so re-pulling the same NCM codes/period is expected to add duplicate rows, not replace anything.
  - `raw.pulls` — one row per pull, even empty ones: requested codes/period, row count, and `pull_seq` (pulls are ordered by it, not `fetched_at`, which can tie). Reconstructed from `raw.exports` for older pulls on every connection and staging build.
  - `staging.dim_ncm` — upserted (not replaced) from `ncm_codes.py` on every `get_connection()` call, so its code/description/category columns can't drift from the source. Its `sh6_code`/`unit` columns are populated separately by `refresh_ncm_hierarchy()` (one `/tables/ncm?add=sh` call per tracked NCM code) — upsert rather than replace is what keeps a later `get_connection()` from wiping that enrichment back to null.
  - `staging.dim_ncm_hierarchy` — one row per distinct SH6 group among the tracked NCM codes (several share one, e.g. the bone-in cuts), built by `refresh_ncm_hierarchy()`. Chapter/heading/subheading only — no "Section" level (the API doesn't expose one).
  - `staging.dim_country` / `staging.dim_economic_bloc` / `staging.bridge_country_bloc` — built by `refresh_dim_country()`. Bloc membership is a many-to-many bridge table, not a column on `dim_country` — a country can belong to more than one bloc (e.g. a region and a trade bloc at once).
  - `refresh_ncm_hierarchy()`/`refresh_dim_country()` are explicit/occasional, deliberately **not** run on every `get_connection()` — they make live API calls, and dimension data changes far less often than trade data, so opening a connection shouldn't be coupled to network availability.
  - `staging.exports` — rebuilt from scratch by `build_staging()` (`CREATE OR REPLACE TABLE ... AS SELECT`, not incremental — data volume is small enough that a full rebuild is simpler than upsert logic). For each `(ncm_code, month)`, the most recent pull that *covered* it (per `raw.pulls`, ordered by `pull_seq`) is authoritative - so rows ComexStat drops in a revision drop out here too - and joins `dim_ncm` for name/category. Does **not** currently join `dim_ncm_hierarchy` or the country/bloc tables — that's left for Phase 2 analysis to wire in when actually needed.
  - `marts.exports` — rebuilt from `staging` by `build_marts()`, adds `kg / 1000.0 AS metric_ton`, and drops Brazil itself as a destination (`BRAZIL_CO_PAIS = "105"`, ~$204k of re-imports/returns — not an export market; `staging` keeps those rows). Uses `IS DISTINCT FROM`, so rows with a NULL `co_pais` (unmatched country) are kept. `category` stays a plain column, not rolled up across categories — cross-category weight comparability (e.g. canned/processed beef's net weight isn't directly comparable to a frozen cut's) stays an open, query-time question rather than baked into the schema.
  - `staging.exports`/`marts.exports` don't exist until their build function has run at least once — querying them before that fails loudly rather than silently returning zero rows.

- `refresh.py` — the routine monthly refresh (`uv run python -m dv_beef_exports.ingestion.refresh [--force]`): checks `/general/dates/updated`, re-pulls the previous calendar year through the newest published month (ComexStat revises published months), refreshes country dims, rebuilds staging/marts, then gates the result - per-country rows must sum exactly to ComexStat's per-code totals (fails otherwise), new months far off the 12-month median are flagged, revisions are listed. Writes a markdown summary. Run weekly by `.github/workflows/refresh.yml`, which opens a PR with the refreshed DB using the `REFRESH_PAT` secret (ADR 0003 amendment).

The tracked `comexstat.duckdb` holds the full backfill: all 11 NCM codes × 1997–present, 72,724 rows in `staging.exports`/`marts.exports`.

**Analysis** (`analysis/`):
- `opportunity_scoring.py` — `rank_markets()` (fix a product, rank geographies) and `rank_products()` (fix a geography, rank products) are thin wrappers over one shared `_score_opportunities()` query, parametrized by `product_level`/`geo_level` (`ncm_code`/`category`/`overall` and `country`/`region`/`trade_bloc`/`overall`) so both lenses stay one query shape, not two hand-kept-in-sync copies. `opportunity_score` is a 0-100 **opportunity index** (ADR 0006, replacing 0005's growth × (1 − share)): `100 × attractiveness × headroom × materiality × evidence`. Attractiveness = weighted percentile ranks within the ranked set (`INDEX_WEIGHTS`: 30% long-run growth, 30% recent momentum = recent growth + consistency over the last `RECENT_PERIODS`=4 periods, 20% log size, 20% price trend); headroom = 1 − share as a multiplier (saturated markets don't win on size); materiality = tons/yr ÷ (tons/yr + `CONTAINER_TONS`=25, ~one reefer container); evidence = 0.5 + 0.5 × confidence. Component columns are part of the output. `confidence` is still the geometric mean of years-coverage, adjusted-R² trend fit, and volume confidence (ADR 0005). Groups with fewer than `min_years_active` (floor 4) active years in the trailing `window_years` are dropped — adjusted R² is undefined/unstable below that. A "year" is a **trailing 12-month period ending at the latest month in `marts.exports`** (`periods_ago`, via `_PERIODIZED_SQL`), not a calendar year, so a partial current year is never scored as a full one (ADR 0005 amendment, 2026-10-03); `latest_period_end()` returns where that period ends. Before the fit, leading periods worth < 1% of the group's median period are trimmed as noise (`_LEADING_TRIM_FRACTION`; leading-only so a recent collapse is never hidden — ADR 0005 amendment). `docs/analysis-methodology.md` is the per-metric reference (formula + worked example against the real DB + how to read it + where it misleads); it also records the known distortions in the current output (the trim reading a post-gap ramp as a new market, `K`'s low bar).
- `market_overview.py` — the descriptive Phase 2 metrics, on the same trailing 12-month periods (`_PERIODIZED_SQL`) so figures agree with the scores. `market_trend()`: value, tons, sum-then-divide $/t, destination count and YoY per period, for any product × market scope. `top_destinations_matrix()`: top N destinations (country/region/trade bloc, ranked by value or tons via `rank_by`) × products (NCM/category) over the latest 12 months, as a full long-format grid with value, tons, $/t, YoY for each, and shares. Shares `level_filters()` / `latest_month_index()` / `add_period_bounds()` with `opportunity_scoring.py`.

**App** (`app/`):
- Three-page Streamlit app (`st.navigation`). `main.py` is the entry point: for the two ranking pages it renders the shared sidebar query (goal: best markets / best products; one searchable product or market picker; what to compare; `window_years`/`min_years_active` under "Advanced") and runs it **before** the page, storing `st.session_state.query`/`.result`, so both always show the same selection. The sidebar is skipped on the overview page; its widgets use `persist_state="session"` (via `common._keep()`) so the query survives the visit — without it Streamlit resets widgets that aren't rendered. Reads the tracked `comexstat.duckdb` directly via `common.connection()` — no separate app-layer data access.
- `common.py` — connection, sidebar controls, query, display labels/formats, `display_name()` (products always shown by name, never bare NCM code), `period_label()` ("Sep '25–Aug '26" on every chart axis), `MONEY_AXIS_LABELS`/`TONS_AXIS_LABELS` ("$20B", not 20,000,000,000), `query_summary()` (the current query in one line at the top of each ranking page — the sidebar hides behind ☰ on phones), and `PRODUCT_PHRASES`/`CATEGORY_PHRASES` (how each product reads mid-sentence — ComexStat's list-style names like "Livers, frozen" don't).
- `app_pages/overview.py` — the landing page: its own product/market pickers, a plain-language headline (incl. whether value growth came from volume or price, `explanations.growth_drivers()`), four KPIs, a 12-month trend chart, and a destinations × products **HTML table** (`st.html`: scrolls sideways on a phone with the destination column pinned, where an Altair heatmap squeezed every cell) that follows the trend chart's measure picker and is **coloured per column** (darkest = that product's top destination; one scale across the grid would only show that frozen cuts are big), with a warning when one destination dominates.
- `app_pages/opportunities.py` — Altair bar chart (top 15 by `opportunity_score`) plus the full ranked table, whose column-header tooltips come from `opportunity_scoring.METRIC_GLOSSARY` (kept word-for-word in sync with the methodology doc's quick-reference table by a test), and a "How to read these numbers" expander.
- `app_pages/explain.py` — "Explain the numbers": pick one result, get a bottom-line verdict plus every metric explained for a business reader (what it means / for your selection, with real numbers / what to do with it), and the result's period-by-period history against its fitted trend (`opportunity_scoring.period_history()`, which shares the scoring query's window + leading-trim CTEs via `_trimmed_periods_ctes()`).
- `explain_charts.py` — the Explain page's charts: under every metric, a **context** chart (the metric over time or what it's made of) and a **comparison** chart (`comparison_chart()`: top 10 of the ranked set, the selected result highlighted in blue and every other grey, appended with its rank if outside the top 10). Every chart is titled (title names it, subtitle says how to read it; `style_chart()` styles titles); no dual axes — value and tons are two stacked charts. Pure functions, schema-checked in tests.
- `explanations.py` — the explain page's wording, as pure functions (no Streamlit) so every sentence is unit-tested. Value bands pick the action text and mirror the methodology doc's readings; flags a trade with no sales in the latest 12 months.

- `.streamlit/config.toml` forces the light theme — the chart greys and the HTML table are styled for a light background.

**Data directory conventions** (`.gitignore`):
- `data/processed/comexstat.duckdb` — tracked in git (small, narrow NCM scope; doubles as change history — see ADR 0003). Everything else in `data/processed/` is ignored.
- `data/raw/` — gitignored scratch, regenerable, not the asset.
- `data/samples/` — gitignored reference-only sample data (bulk CSVs, dimension tables) used to design against real shapes; not part of the pipeline itself.

## Conventions

- Branches: `feat/<name>`, `fix/<name>`, `chore/<name>`; PRs squash-merged into `main` (`docs/WORKFLOW.md`).
- Commits: conventional-commit prefixes (`feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`).
- Add an ADR under `docs/decisions/` only for choices that would be confusing to re-derive later (data source, library, storage/schema shape) — not routine implementation details. Update `docs/DEVLOG.md` when a PR lands something worth remembering.
- API tests use `requests_mock`; DuckDB tests use `tmp_path` for an isolated `.duckdb` file per test (see `tests/ingestion/`).
